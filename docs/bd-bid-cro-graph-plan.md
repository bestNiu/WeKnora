# BD竞标知识库 · CRO 领域知识图谱建设方案（规划稿）

> 目标：打开「BD竞标」知识库的图谱能力，把 378 份竞标 PPT 建成 **以项目为核心、业绩为属性、PPT 页为证据** 的 CRO 领域图谱，
> 未来输入一个新的竞标需求，AI 能自动关联历史项目、适应症经验、服务能力、团队与交付证据。

- 知识库：`BD竞标`（`128316d5-f301-44f2-95f1-ea29c6b69aa7`）
- 现有内容：378 份文档（365 pptx + 13 pdf，9.45 GB），47,270 chunks，全部 `parse_status=completed`
- 页级定位：47,270 个 chunk 中 **9,777 个已带 `source_locators`（含 `slide` 页码 + 原文 quote）**，可直接做"原 PPT 第 N 页"引用
- 图谱现状：Neo4j 2025.10.1 + APOC 可用（`apoc.merge.node` 实测通过），当前 **0 个节点**，KB `graph=false`

---

## 0. 结论先说：能做，但有 3 个能力边界必须接受或绕开

| # | 平台现状（实测） | 影响 | 本方案的处理 |
|---|---|---|---|
| 1 | 图谱节点只存 `{name, attributes[], chunks[]}`，**实体类型不落 Neo4j 标签**（标签只有 KB 级空间标签） | 不能直接 `MATCH (p:临床试验项目)` | P0 把类型写成 `attributes` 里的 `类型=…` 前缀；P1 改代码升级为真标签 |
| 2 | 抽取粒度是 **chunk（约 512 字）**，不是整份 PPT | 跨页事实（项目 → 30 家中心、240 例）可能被切散 | P0 靠"项目代号锚点 + 属性自述"约束；P1 改按 slide 切分 + 项目级聚合 |
| 3 | 已入库文档**不会自动补图谱**，只有重新解析才跑抽取 | 378 份要回填 | 用 `batch-reparse` 批量重跑（见 5.2），会产生 LLM 与重嵌入成本 |

另外两个必须先知道的机制：

- **关系类型是自由的**：LLM 输出的关系名直接成为 Neo4j 关系类型（中文可以，Cypher 里要反引号）。代码里 `RemoveUnknownRelation` 目前被注释掉，即**不做白名单过滤** → 关系类型必须在提示词里强约束，否则会碎。
- **实体类型标签（tags）只进提示词**：`tags` 会注入 system prompt 的 EntityTypes 槽位（≤50 个），few-shot 示例里的节点只渲染 `name + attributes`，不带 type。所以"16 类实体"这个约束的实际抓手是 **额外提取要求 + 示例里的 `类型=` 属性**，不是 tags 本身。

## 2. 设计原则（对齐你的业务要求）

1. **项目是核心实体**：`项目代号 / 项目名称` 为一级节点，历史案例优先按项目聚合。
2. **业绩是项目的事实属性**：`实际入组 300 例` 不能脱离项目单独存在 → 写成项目的 `attributes`，并标注来源项目与页码。
3. **PPT 是证据**：节点/关系 → chunk → `source_locators.slide` → 原 PPT 第 N 页 + 原文片段。
4. **区分计划与承诺**：投标阶段的"拟入组 240 例"与历史项目的"实际完成 300 例"必须分开标注，禁止混算为业绩。
5. **不推测**：文本没写的合作、业绩、中心一律不生成；不提取受试者个人信息。
6. **服务能力要带主体**：`临床运营` 这种泛化词会成为巨型节点，统一写成 `有临-临床运营`（能力归属有临）。

## 4. 配置落地：三个字段怎么填

> 路径：`知识库 → BD竞标 → 设置 → 知识图谱`。三个字段的硬限制：**额外提取要求 4000 字 / 示例文本 5000 字 / 实体类型 ≤50 个**。

### 4.1 实体类型（tags，16 个）

```
申办方, 临床试验项目, 适应症, 研究药物, 临床阶段, 试验设计, CRO服务能力, 研究中心, 研究者, 业绩指标, 团队岗位, 技术平台, 质量标准, 地理区域, 交付物, 商务模式
```

> 只放这 16 个，不要放关系名（关系名走"管理关系"）。上限 50，留出后续扩展空间。

### 4.2 关系类型（18 个，在"管理关系"里逐个添加，或在"开始提取"后修正）

```
参与竞标, 委托, 承接项目, 涉及适应症, 研究药物, 处于临床阶段, 采用试验设计, 设置研究终点, 覆盖研究中心, 担任PI, 提供服务, 使用系统, 配置团队, 取得业绩, 产出交付物, 遵循质量标准, 覆盖地区, 合作
```

### 4.3 额外提取要求（customInstructions，可直接粘贴，约 1150 字）

```
请针对 CRO 临床试验竞标 PPT 做专业领域实体关系抽取，只提取文本中明确写出的事实，不推测、不补全。

一、实体类型（必须是以下 16 类之一，写在 attributes 里，格式固定为「类型=xxx」）
申办方、临床试验项目、适应症、研究药物、临床阶段、试验设计、CRO服务能力、研究中心、研究者、业绩指标、团队岗位、技术平台、质量标准、地理区域、交付物、商务模式。

二、命名规范
1. 项目：优先用项目代号；无代号时用「药物+适应症+分期」。同一项目的不同叫法必须归一为同一个名称。
2. 适应症：用规范病名，英文缩写写进 attributes，如「别名=NSCLC」。
3. 服务能力：必须带主体前缀，如「有临-临床运营」「有临-数据管理」，不要出现光秃秃的「临床运营」。
4. 医院写全称；研究者写「姓名(医院)」。
5. 业绩指标写成「项目代号-指标名」，如「UC-2024-003-实际入组」。

三、事实与承诺必须区分（最重要）
1. attributes 必须带「事实类型=实际」或「事实类型=计划」。
2. 「曾完成/实际覆盖/已完成入组/已锁定数据库」→ 实际；「拟/计划/预计/将提供」→ 计划。
3. 计划信息不得生成「取得业绩」「产出交付物」关系。
4. 数值保留原单位与统计时点，如「300例」「40家」「统计时点=DBL」；没有数值就不要编造。

四、关系（只用以下 18 种，方向固定为 主语→宾语）
参与竞标、委托、承接项目、涉及适应症、研究药物、处于临床阶段、采用试验设计、设置研究终点、覆盖研究中心、担任PI、提供服务、使用系统、配置团队、取得业绩、产出交付物、遵循质量标准、覆盖地区、合作。

五、禁止
1. 不提取受试者个人信息、联系人、手机号、邮箱。
2. 不生成文本未明确支持的合作、业绩、中心、专家。
3. 同一句里的计划数字不要挂到历史项目上。
4. 不要输出解释性文字，只输出 JSON。

六、语言
实体名称保持原文；描述与属性用中文。
```

### 4.4 示例文本（text，可直接粘贴你给的虚构案例，约 470 字）


## 5. 实施路径

### 阶段 0：开图 + 小样验证（0.5 天，无代码）

1. 按第 4 节填完四个字段并保存，开关打开。
2. 选 **3 份 PPT**（建议：1 份历史 III 期案例、1 份 II 期竞标、1 份含中心/团队明细）逐份 `reparse`：
   `POST /api/v1/knowledge/{knowledge_id}/reparse`
3. 等 enrich 队列跑完（看 `knowledge_spans` 或日志 `nodes_added`），用 Cypher 抽查：
   ```cypher
   MATCH (n) WHERE n.kg = "<knowledge_id>" RETURN n.name, n.attributes LIMIT 50;
   MATCH (a)-[r]->(b) WHERE a.kg = "<knowledge_id>" RETURN a.name, type(r), b.name LIMIT 50;
   ```
4. 用 `POST /api/v1/knowledge-bases/{kb}/graph-search` 查「NSCLC」「UC-2024-003」，确认能带出节点+关系+关联 chunk。
5. **验收门槛**（决定是否全量）：项目节点 100% 带 `类型=`；18 种关系之外 0 条；计划/实际标注正确率 ≥90%；抽 10 条关系能回溯到 slide。

### 阶段 1：全量回填 378 份（1–2 天，主要是排队时间）

| 项 | 估算 |
|---|---|
| 待抽取 chunk | 47,270（每 chunk 一次 LLM 调用） |
| 单次输入 token | ≈ 2,500–3,500（全局模板 + 4000 字要求 + 示例 + chunk），**大头是固定前缀** |
| 总输入 token | ≈ 1.2–1.7 亿 |
| 总输出 token | ≈ 1,200 万（每 chunk 约 250） |
| 墙钟时间 | 4 并发 × 单次 2–4s ≈ **7–13 小时** |
| 成本 | `输入token/1e6 × 输入单价 + 输出token/1e6 × 输出单价`（按你们 qwen3.8-max 的实际单价算；若走 litellm 缓存，重复前缀可大幅降低输入成本） |

执行方式：
- 分批 `batch-reparse`（建议 30 份/批），每批完成后再放下一批，避免 enrich 队列打满影响检索；
- 优先回填 **P0 价值最高** 的文档：历史 III 期案例、含中心/PI 明细、含业绩数字的 PPT（可用文件名/大小筛选）；
- 回填期间观察：`nodes_added` 失败率、Neo4j 节点数增长、LLM 429。

> 成本敏感时的替代：先只回填 50–80 份（≈6k–10k chunk，输入 ≈2,000 万 token），验证业务价值后再决定是否全量。

### 阶段 2：代码增强（P1，2–3 天）

| # | 增强项 | 改动点 | 价值 |
|---|---|---|---|
| 1 | **实体类型落 Neo4j label** | `GraphNode` 增 `Type`；`chat_pipeline` 解析 type；`neo4j.addGraph` 用 `[类型] + 空间标签` 作为 labels | `MATCH (p:临床试验项目)` 才能做 | 
| 2 | 关系白名单 | 恢复 `RemoveUnknownRelation`，白名单取 18 种 | 防关系爆炸 |
| 3 | **按 slide 切分 chunk** | chunker 支持以 `source_locators.slide` 为边界 | 一页一事实，项目属性不被切散 |
| 4 | 项目级属性聚合 | 抽取后按项目节点合并 attributes（去重） | "某项目全部业绩"一次查全 |
| 5 | 计划/实际结构化 | attributes 里固定 `fact_kind=actual|planned` + `as_of` | 防止承诺当业绩 |
| 6 | 证据链返回 | graph-search 结果附 `文件名 + slide + quote` | 前端直接显示"原 PPT 第 12 页" |
| 7 | 同义词归一 | 别名字典（NSCLC↔非小细胞肺癌、有临↔有临医药） | 减少重复节点 |
| 8 | 仅重建图谱的开关 | 新增 graph-only reprocess 任务 | 省掉重复 embed 的钱 |
| 9 | 竞标匹配接口 | 输入需求文本 → 相似项目 + 能力 + 业绩证据 | 直接支撑标书生成 |

> 1/3/5/6 是把你这套 schema 真正"落成结构化"的关键，P0 阶段用提示词只能做到"大概对"，做不到"能按类型查"。

## 6. 会踩的坑（提前说清）

| 坑 | 现象 | 对策 |
|---|---|---|
| 实体类型不落 label | 想按类型查只能 `WHERE n.attributes CONTAINS '类型=临床试验项目'`（慢） | P1 改 label |
| 泛化词变巨型节点 | "项目管理""临床运营"聚合几百条边 | 强制 `有临-` 前缀 |
| 项目名不统一 | `UC-2024-003` / `UC-2024-003 项目` / `UC2024003` 三个节点 | 提示词要求归一 + P1 别名字典 |
| 计划数字串到历史项目 | 竞标承诺被算成业绩 | 提示词三段式约束 + 阶段 0 人工抽检 |
| chunk 切断单页信息 | 一页表格被切成 2 个 chunk，中心数只抽到一半 | P1 按 slide 切 |
| 重复 embed 花钱 | reparse 会重跑向量化 | P1 graph-only 重建 |
| 关系类型自造 | 出现"参与""负责"等近义关系 | 提示词 + P1 白名单 |
| 中文关系名 | Cypher 需反引号，手查不方便 | 文档里给现成查询模板 |

## 9. 需要你确认的 5 件事

1. **关系名用中文还是英文？** 中文可读性好、Cypher 需反引号；英文（如 `INVOLVES_INDICATION`）查起来更顺手。建议**中文**（与你给的清单一致），P1 如需对接外部图库再映射。
2. **接受"实体类型先写 attributes、P1 再升级 label"吗？** 不接受就得先做阶段 2 的第 1 项，再开全量回填（顺序要调）。
3. **全量回填预算上限？** 按 1.4 亿输入 token 估算，给个上限我就按"先 50 份 → 再 378 份"分批推。
4. **"计划/实际"是否作为硬约束？** 建议是（我方口径上最容易被质疑的点）。P0 靠提示词，P1 做结构化字段。
5. **是否需要"可对外引用"标记？**（涉密/未授权项目只入库不出现在竞标生成里）——需要的话列入 P1 第 8 项。

## 附录 A：Cypher 查询模板（回填后自测用）

```cypher
// 某个知识库的全部实体（按类型人工抽查）
MATCH (n) WHERE n.kg = '<knowledge_id>'
RETURN n.name AS 名称, n.attributes AS 属性
ORDER BY 名称 LIMIT 100;

// 某适应症下的所有项目及其阶段
MATCH (p)-[r:`涉及适应症`]->(i)
WHERE p.kg = '<knowledge_id>' AND i.name CONTAINS '非小细胞肺癌'
OPTIONAL MATCH (p)-[s:`处于临床阶段`]->(st)
RETURN p.name, st.name AS 阶段, p.attributes;

// 某项目的全部业绩与证据 chunk
MATCH (p {kg:'<knowledge_id>'})-[:`取得业绩`]->(m)
RETURN p.name, m.name, m.attributes, m.chunks;

// 关系类型分布（检查有没有自造类型）
MATCH (a)-[r]->(b) WHERE a.kg = '<knowledge_id>'
RETURN type(r) AS 关系, count(*) AS 数量 ORDER BY 数量 DESC;
```

## 附录 B：为什么要"先小样再全量"

- 抽取是 **per-chunk** 的，378 份 = 47,270 次调用，提示词固定前缀占输入 token 的 80% 以上，**改一版提示词就要重跑一遍**；
- P0 用提示词约束"类型/计划-实际/归一"，正确率通常 70–90%，先拿 3 份 PPT 看到偏差再全量，能省掉一轮 1.4 亿 token；
- 全量前把"类型=""事实类型="写法固化进提示词与示例，后面 P1 升级 label 时可以用同样的字符串做数据迁移。

## 附录 C：实施实测记录（2026-10-28）

### C.1 提示词路线的 4 个必要改造

| # | 改造 | 原因 | 效果 |
|---|---|---|---|
| 1 | enrich 并发 4→12（32 会打爆网关） | 单次抽取 198s，4 并发仅 1.8 次/分 | 16s/次，12 并发 ≈40 次/分（22 倍） |
| 2 | `tags` 只放 18 个**关系类型** | 平台把 `tags` 注入 system prompt 的「Allowed relationship types」槽位；放实体类型会导致关系全废（实测 0 条） | 关系即刻正确，无自造类型 |
| 3 | 空响应按"跳过"处理 + 开关系白名单 | 空响应原本触发 3 次重试（烧 token）；关系无白名单会碎 | 失败率 80% → 1~4% |
| 4 | 新增 `POST /knowledge/:id/graph/rebuild`（可选 `chunk_ids`） | 改提示词要重跑全部 chunk，但不能重解析/重嵌入 | 单文档重建 3 分钟，不再重付 embedding |

### C.4 已知限制

1. `graph-search` 是**实体名子串查询**（大小写敏感），不是语义检索；聊天链路里由实体抽取先产出实体名再查，直接拿自然语言问它会返回 0。
2. 页级引用依赖解析器给出的 `source_locators`：本 KB 47,270 个 chunk 中 9,777 个有 slide 号，其余无页码（表格/图片页较多）。
3. 重复执行 `graph/rebuild` 是幂等的（节点按 (name, knowledge) 合并），可以放心重试。
